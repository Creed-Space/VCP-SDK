# VCP coordinated release runbook

This runbook turns the remaining human, rights, governance, deployment, and
publication gates into an auditable release process. It does not grant any
review or publication authority. A machine result cannot be substituted for a
named human decision, legal opinion, independent assessment, registry action,
or production observation.

## 1. Evidence model

Every decision is bound to one exact three-repository candidate. Evidence from
an earlier commit, a dirty working tree, a rebuilt binary, or a different
deployment does not transfer automatically.

The release record consists of:

1. A candidate source manifest generated by
   `scripts/build_candidate_manifest.py`.
2. A copy of `release/review-ledger.template.json` completed by authorized
   reviewers.
3. Machine validation logs, package inventories, checksums, and dependency and
   secret scan reports.
4. Human review reports from the Demo, Spec, and SDK review packs.
5. Legal, governance, editorial, and independent security decisions.
6. Signed source and package artifacts, registry receipts, and immutable tags.
7. Deployment identity, production smoke evidence, and rollback evidence.

Keep source evidence, package evidence, deployed-runtime evidence, human
evidence, rights evidence, and publication authority distinct. A successful
build proves none of the other categories.

## 2. Roles and separation of duties

Assign names before freezing a release candidate.

| Role | Responsibility | May be combined? |
|---|---|---|
| Release coordinator | Maintains candidate identity, sequencing, and ledger integrity | May also be a maintainer |
| Machine evidence owner | Runs reproducible checks and records logs | May also be a maintainer |
| Legal reviewer | Decides trademark, patent, licence, contribution, and redistribution posture | Must have the required authority |
| Protocol reviewer | Reviews normative protocol and cryptographic assumptions | Independent from the implementation authors for X017 |
| SDK security reviewer | Reviews signature, revocation, and scope enforcement | Independent from the implementation authors for K045 |
| Accessibility reviewer | Performs keyboard and assistive technology review | Must use the named candidate and environment |
| Privacy reviewer | Compares deployed behavior with public privacy language | Must inspect runtime network and storage behavior |
| Governance authority | Fills seats, handles conflicts, establishes quorum, and records votes | Defined by the adopted governance process |
| Editorial authority | Selects canonical publication artifacts | Must record exact artifact hashes |
| Registry publisher | Uses protected registry credentials and records receipts | Must be explicitly authorized |
| Deployment owner | Approves production deployment and rollback | Must control the production service |

Independent reviewers must disclose prior authorship, financial interests,
employment, close collaboration, and other conflicts. The disclosure belongs
in `reviewer.independence_statement` even when the reviewer concludes that no
conflict exists.

## 3. Prepare the release evidence directory

Create an access-controlled directory outside all three repositories. Do not
place credentials or private legal advice in a public repository. Suggested
layout:

```text
vcp-release-evidence/
  candidate-manifest.json
  review-ledger.json
  machine/
  accessibility/
  privacy/
  governance/
  editorial/
  legal/
  security/
  packages/
  deployment/
  rollback/
```

Copy the ledger template:

```bash
cp release/review-ledger.template.json \
  /secure/path/vcp-release-evidence/review-ledger.json
```

Never edit the repository template into an apparently approved state. The
template is intentionally and permanently pending.

Never commit the working ledger into a candidate repository. Besides exposing
review material that may be access-controlled, doing so would change the SDK
tree hash recorded inside the ledger and create a self-referential candidate.

## 4. Freeze and identify the candidate

### 4.1 Candidate prerequisites

1. Land reviewed changes in each repository through its normal branch process.
2. Confirm there are no staged, modified, deleted, or untracked candidate
   paths in any release checkout.
3. Confirm each checkout points to the intended branch and commit.
4. Confirm no generated build directory, secret, source symlink, special file,
   or file larger than 50 MiB is present in the candidate.
5. Stop if another maintainer owns a dirty checkout or active release process.

### 4.2 Build the candidate manifest

Run from VCP-SDK, writing outside every candidate repository:

```bash
python scripts/build_candidate_manifest.py \
  --demo /path/to/VCP-Demo-Site \
  --spec /path/to/VCP-Spec \
  --sdk /path/to/VCP-SDK \
  --require-clean \
  --output /secure/path/vcp-release-evidence/candidate-manifest.json
```

Record these values in the review ledger:

1. Each repository commit and `working_tree_sha256`.
2. `combined_candidate_sha256`.
3. The SHA-256 of `candidate-manifest.json` as
   `source_manifest_sha256`.
4. Protocol baseline, amendment, maturity, and all distribution versions.

Any source change invalidates the freeze. Generate a new manifest, invalidate
all evidence that depended on the old candidate, and restart the affected
gates.

## 5. Run machine acceptance

Use clean, locked environments. Preserve complete logs and hash each log before
linking it from a review record.

### 5.1 Integrated acceptance

```bash
python scripts/validate_ecosystem.py \
  --demo /path/to/VCP-Demo-Site \
  --spec /path/to/VCP-Spec \
  --sdk /path/to/VCP-SDK \
  --python /path/to/locked/python \
  --mode full
```

This integrated helper covers exactly Demo, Spec, and the maintained SDK. It
runs maintained-SDK and Demo coverage in `full` mode. The VCP Inspector
(https://github.com/Creed-Space/VCP-Inspector) and the legacy standalone
`vcp-sdk` PyPI package (https://github.com/Creed-Space/vcp-sdk-python) are
validated separately with their own candidate-bound evidence.

### 5.2 New regression programmes

```bash
make property PYTHON=/path/to/locked/python
make performance-smoke PYTHON=/path/to/locked/python
make performance-full PYTHON=/path/to/locked/python
cargo check --locked --manifest-path rust/fuzz/Cargo.toml
```

CI additionally runs bounded fuzz targets on pull requests and longer scheduled
campaigns. Save all discovered crash inputs under the appropriate committed
fuzz corpus before accepting a fix.

### 5.3 Review-ledger validation

The repository template must pass structural validation while remaining
pending:

```bash
python scripts/validate_review_ledger.py
```

Validate the working release ledger after each reviewer update:

```bash
python scripts/validate_review_ledger.py \
  /secure/path/vcp-release-evidence/review-ledger.json
```

Before registry publication, require every decision through X015 while leaving
K044 and X018 available for the receipts and smoke evidence that publication
itself creates:

```bash
python scripts/validate_review_ledger.py \
  /secure/path/vcp-release-evidence/review-ledger.json \
  --require-prepublication
```

The final archival ledger must also pass:

```bash
python scripts/validate_review_ledger.py \
  /secure/path/vcp-release-evidence/review-ledger.json \
  --require-complete
```

`--require-prepublication` requires a final disposition for every gate except
K044 and X018. `--require-complete` requires a final disposition for all 13
decisions, the deployment identity, and the post-publication evidence. Neither
mode reinterprets a rejection or unresolved conditional approval as
authorization.

After prepublication validation passes, bind the exact external ledger to the
protected `vcp-release-approval` environment. The secret carries the private
bytes; the workflow-dispatch input carries their public SHA-256:

```bash
python3 -c \
  'import base64,sys; sys.stdout.write(base64.b64encode(sys.stdin.buffer.read()).decode())' \
  < /secure/path/vcp-release-evidence/review-ledger.json \
  | gh secret set VCP_REVIEW_LEDGER_B64 \
      --repo Creed-Space/VCP-SDK \
      --env vcp-release-approval

shasum -a 256 \
  /secure/path/vcp-release-evidence/review-ledger.json
```

Enter that digest as `review_ledger_sha256` when dispatching `publish`. The
protected job decodes the secret into its temporary directory, checks the
digest before parsing, validates the ledger against the tagged source, and
prints only the digest to its step summary. Delete the environment secret after
the publication workflow finishes and retain the final ledger in the controlled
evidence archive.

## 6. Gate order and dependencies

The recommended order minimizes review invalidation and prevents publication
from outrunning governance.

| Order | Gate | Required input | Output |
|---:|---|---|---|
| 1 | S030 | Governance proposal and conflict disclosures | Seats, quorum, vote record |
| 2 | S031 | Rendered document candidates | Canonical DOCX and PDF hashes |
| 3 | S032 | Amendment evidence and governance record | Explicit v3.2 maturity |
| 4 | S033 | Frozen Spec candidate | Independent privacy, safety, and legal report |
| 5 | D042 | Frozen Demo candidate and review environment | Accessibility report |
| 6 | D043 | Release-like or production Demo | Privacy report and network capture |
| 7 | K045 | Frozen SDK candidate | Independent SDK security report |
| 8 | X017 | Frozen Spec and SDK candidates | Independent protocol and cryptographic report |
| 9 | X016 | All source, notices, assets, packages, and prior reports | Authorized legal opinion |
| 10 | K046 | Compatibility diff and reviewer findings | Semver decision |
| 11 | X015 | All prepublication decisions and machine evidence | Exact candidate and release-order approval |
| 12 | K044 | Approved candidate, versions, credentials, signing policy | Signed registry releases and receipts |
| 13 | X018 | Published packages and deployed Demo | Production and registry smoke report |

D043 may begin in a release-like environment, but it remains open until the
authorized reviewer checks the deployed candidate. X018 can only close after
publication and deployment.

## 7. Gate completion rules

Every completed ledger record requires:

1. A named reviewer, role, organization, and independence statement.
2. A timestamp and a substantive decision summary.
3. Findings with severity and disposition, including an explicit empty-finding
   statement in the report when no findings were identified.
4. Required evidence kinds with content SHA-256 values.
5. An attestation method, identity, timestamp, and signature or approval value.
6. Conditions recorded separately from findings.

`approved_with_conditions` blocks publication until every condition has
objective closure evidence and the decision is updated. `not_applicable`
requires the same authority and evidence as any other decision. It is not a
shortcut around a required gate.

### 7.1 Waiving an independent gate

X017, S033, and K045 require a reviewer who is independent from the candidate's
authors. When no such review exists, the release authority may record the gate
as `waived` instead of fabricating independence. A waiver is a visible,
auditable statement that the review did not happen; it is never a claim that it
did. The validator accepts `waived` only for those three gates and only when
the record carries:

1. The waiving authority as `reviewer`, with an `independence_statement` that
   discloses that authority's relationship to the candidate (for example,
   "author and interim administrator; not independent").
2. A `decision_summary` of at least 100 characters stating why publication is
   proceeding without the review, what the residual risk is, and when the
   review is expected.
3. Evidence of kind `waiver-record`: the hashed written rationale, stored in
   the controlled evidence directory.
4. The usual `reviewed_at` and `attestation`.

Public copy for a release with waived gates must not claim independent review.
Record the waiver in the status registry's residual-risk register and reopen
the gate as `pending` in the next candidate's ledger.

## 8. Coordinated publication sequence

Only X015 authorizes the exact sequence. The default dependency-safe sequence
is:

The manual `SDK release candidate and publication` workflow implements this
sequence in two modes. `dry-run` builds twice from clean checkouts, compares
every delivered byte, generates CycloneDX SBOMs and a final SHA-256 manifest,
and requests GitHub artifact attestations. `publish` additionally requires an
exact signed `v<version>` tag, the protected `vcp-release-approval`
environment, a coordinated ledger that passes `--require-prepublication`,
an exact dispatch digest for the protected external ledger, ratified package
names, and registry-specific protected environments. K044 and X018 are then
completed from the publication receipts and production smoke evidence before
the ledger passes `--require-complete`. The current source-only publication
state deliberately causes publication preflight to fail.

1. Create signed, immutable repository tags for the approved Spec and SDK
   commits. Record tag-object hashes and signature verification output.
2. Publish the canonical Spec artifacts and record their hashes, location, and
   maturity label.
3. Rebuild all SDK distributions from the approved clean SDK commit in the
   protected publication environment.
4. Compare rebuilt package inventories and hashes with the reviewed package
   evidence.
5. Publish `vcp-core` first. Verify the registry serves the exact intended
   version and checksum.
6. Rerun package verification for `vcp-cli` and `vcp-wasm` against the published
   exact `vcp-core` dependency, then publish those crates if authorized.
7. Publish `value-context-protocol` to the authorized Python registry and
   `@creed-space/vcp-sdk` to the authorized npm registry.
8. Verify each registry from a fresh environment, with no local path overrides
   and no warm package cache.
9. Deploy the approved Demo commit through the production service's authorized
   release path. Record deployment ID, environment, URL, timestamp, and source
   commit.
10. Run D043 and X018 against that deployment and the published package set.
11. Archive the completed ledger, receipts, checksums, signatures, logs, and
    rollback outcome.

Do not publish a replacement artifact under an existing immutable version. If
a package differs, stop and choose a new version through K046.

Cargo has one explicit tool-boundary exception. `cargo publish` creates the
`.crate` archive as part of the upload operation and has no supported option to
upload a previously staged archive. The workflow therefore packages each crate
immediately before publication, compares that archive byte for byte with the
already attested archive, then lets Cargo package and upload from the same clean
checkout. The registry receipt and registry checksum must be compared with the
attested digest. A mismatch stops the release and requires a new version.

## 9. Signing and provenance requirements

The release authority chooses an approved signing mechanism. At minimum,
retain:

1. Signed Git tag verification for every released repository commit. The
   publish workflow imports the ASCII-armored public keys held in the
   protected `VCP_RELEASE_SIGNING_KEYS` repository/environment variable before
   running `git verify-tag`; rotate a key by replacing that variable and
   recording the new fingerprint in the review ledger.
2. SHA-256 inventories for source archives, wheels, sdists, crates, npm
   tarballs, canonical documents, and deployment bundles.
3. Registry receipts and registry-reported checksums where available.
4. Build environment identity, tool versions, and dependency locks.
5. Provenance attestation that names source commit, builder, invocation, and
   artifact digest.
6. Signature verification output from a clean environment.

Credentials belong in the authorized platform secret store or macOS Keychain,
not in environment files, shell history, logs, evidence bundles, or repository
configuration.

## 10. Production and registry smoke testing

X018 must exercise what users receive, not local source:

1. Install each published SDK in a fresh environment by exact version.
2. Verify package name, version, exported API, licence, notices, and checksum.
3. Run one documented signing and verification flow for each supported SDK
   distribution.
4. Verify a confirmed revocation, an explicitly clear revocation response, and
   an unavailable revocation source. Unavailable must fail closed where policy
   requires revocation checking.
5. Verify scope rejection and one permitted operation.
6. Exercise the deployed Demo checklist in
   `reviews/ACCESSIBILITY_PRIVACY_PRODUCTION_REVIEW.md` in VCP-Demo-Site.
7. Capture TLS, security headers, network requests, storage, console errors,
   and server-side release identity without capturing secrets or user content.

## 11. Stop conditions

Stop the release immediately when:

1. Candidate hashes do not match the ledger.
2. A reviewer examined another candidate or deployment.
3. A critical or high finding is unresolved.
4. Any required gate is pending, rejected, or conditionally approved with an
   unresolved condition.
5. A package rebuild differs without an explained, reviewed reproducibility
   exception.
6. A signature, registry checksum, deployment identity, or canonical document
   hash cannot be verified.
7. Secrets or private review material appear in a public artifact.
8. The deployed runtime sends unexpected analytics, exposes sensitive context,
   or contradicts public privacy language.

## 12. Rollback and incident record

Before publication, name owners and exact procedures for:

1. Disabling or reverting the Demo deployment.
2. Yanking or deprecating packages without deleting audit history.
3. Publishing corrected packages under new immutable versions.
4. Revoking compromised signing keys and affected bundles.
5. Correcting Spec maturity or errata without rewriting signed artifacts.
6. Notifying users and reviewers of evidence invalidation.

After a rollback, preserve the failed release evidence. Record trigger,
timeline, affected versions, user impact, containment, corrective action, and
the candidate identity of the replacement.

## 13. Repository-specific review packs

Use these documents as the authoritative worksheets:

1. VCP-Demo-Site:
   `reviews/ACCESSIBILITY_PRIVACY_PRODUCTION_REVIEW.md` for D042, D043, and the
   Demo portion of X018.
2. VCP-Spec:
   `reviews/GOVERNANCE_EDITORIAL_INDEPENDENT_REVIEW.md` for S030 through S033,
   plus Spec inputs to X016 and X017.
3. VCP-SDK: `reviews/SDK_SECURITY_SEMVER_PUBLICATION_REVIEW.md` for K044 through
   K046, plus SDK inputs to X017 and X018.

The completed reports are evidence inputs. The ledger is the cross-repository
index and attestation record.
